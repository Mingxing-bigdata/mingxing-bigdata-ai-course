1 一句话关系

Agent 是会“动手做事”的系统，Context 是它每次思考时那张大小有限的“临时工作台”，Skill 是它放在手边、按需翻阅的“专业操作手册”。三者组合，才构成“通用模型 → 稳定完成专业任务”的完整闭环。

流程要点：Skill 平时不进 Context，匹配后才“按需注入”；工具结果必须先写回 Context，模型才能“看见”。

4 重点①：上下文如何影响 Agent 的工作

  1. 决定“记性”好坏：Agent 没有真正的记忆，能“想起来”的只有被放回上下文的内容。窗口＝短期记忆上限，超出的历史会被截断或遗忘。
  2. 决定“判断依据”：工具返回、检索片段、系统指令先汇入上下文，模型才据此决定下一步。给错信息＝做错决策。
  3. 决定“任务复杂度上限”：窗口太小 → 长文档/多轮任务装不下 → 需要分块、检索、摘要。扩大窗口本质是扩大 Agent 单次“看得见”的任务规模。
  4. 决定“输出质量”：关键信息放开头/结尾比中间更有效（Lost in the Middle）；上下文塞满噪声会拉低准确率 → 所以要做“上下文工程”：检索最相关、压缩历史、结构化摆放。
一句话：Context 是 Agent 的“内存条”——容量与内容质量，直接决定它能跑多复杂的任务、做得对不对。

5 重点②：Skill 如何沉淀可复用的任务知识

  1. 把隐性经验显性化：把专业流程写成 SKILL.md（步骤＋规范＋自检），经验从“临时发挥”变成“文件资产”。
  2. 通过 description 暴露接口：只暴露一小段触发描述，Agent 判断何时加载——知识在使用时才进入上下文，平时不占“工作台”空间。
  3. 一次沉淀、处处复用：同一 Skill 可在新会话、新 Agent、新任务上复用，还能随 Git 仓库版本管理与共享（如 anthropics/skills）。
  4. 与上下文互补：Skill 用“按需加载”绕开窗口有限的问题；Context 里多一份 Skill 流程，Agent 就“立刻变得专业”。两者配合＝把“有限的上下文”花在“最该用的专业方法”上。

6 一个串起三者的例子（概念学习任务）

  1. 你提出：“帮我系统学一下 XX” —— 用户目标进入 Context；
  2. Agent 读到各技能 description，匹配到 concept-learner Skill，加载其流程；
  3. 流程要求核查一手资料 → Agent 调用 WebFetch 工具，结果写回 Context；
  4. 模型按流程产出结构化学习卡 → 任务完成；本次 Context 作废，但 Skill 仍在仓库，下次学“YY 概念”可再次加载。

这正是本仓库 learning-materials/ 三份资料的生成方式：一个 Skill 一次设计，套用三个概念。
